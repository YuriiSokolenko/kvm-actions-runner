# P0 runner admission incident: social-mcp #795

https://github.com/YuriiSokolenko/social-mcp/issues/795

Status: ROOT CAUSE UNCONFIRMED. Observed old manager logs:
queued=2 busy=0 active=0 desired=1 model_capacity=1 spawning=1
warning: failed to start runner; stopping spawn batch

The old KVM admission predicate is:

    loadavg_1m + guest_vcpus + reserved_cpu <= online_cpus

On N150 (4 CPUs, guest 2 vCPU, reserve 1), it rejects load above 1.0.
This is a hypothesis, NOT proof that CPU admission caused the failure.
The new manager retains this policy until host measurements prove otherwise.

New diagnostics distinguish KVM_CPU_HEADROOM, KVM_DISK_RESERVE,
HOST_MEMORY_RESERVE, HOST_CPU_BUDGET, SCHEDULER_ALREADY_RUNNING,
GITHUB_TOKEN_MISSING, GITHUB_TRANSPORT_ERROR,
EXECUTOR_COMMAND_FAILED and EXECUTOR_TIMEOUT.
Retries are exponential and bounded. The intentionally rejected bare local
proxy readiness connection may log reason=ValueError and is not a guest
egress problem.

Before closing #795: collect non-sensitive host metrics and reason-coded
logs from a real rejected launch, reproduce the identified failure stage
with N150-like fixtures, adjust the admission rule only on evidence, and
verify a queued Recursive Coder CI job eventually runs when the host can
safely accept a VM. Confirm no overlap between VM jobs and existing pools.

Offline CI is NOT production confirmation and cannot prove #795 fixed.
